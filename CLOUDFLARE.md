# TG Alerts: отдельная миграционная версия

Код Render (`server.js`, `prices.js`, исходный интерфейс) не заменён. Рабочий Retocker Access и его webhook не меняются. Этот адаптер предназначен только для отдельного бота TG Alerts.

## Главное ограничение: это НЕ прежний поток котировок

Cloudflare-версия получает **снимки OANDA/Capital примерно раз в 10 секунд**, а не каждый тик OANDA. Короткое касание уровня между проверками может быть пропущено. Задержки API, Telegram и планировщика могут увеличить интервал; доставки к точной секунде нет. Промежуточные цены не выдумываются анимацией, устаревшие/неторгуемые котировки не запускают ценовые алерты и скрываются в интерфейсе.

По умолчанию `SNAPSHOT_QUOTES_APPROVED=false`: запуск и активация заблокированы. Не менять это на `true` без осознанного согласия владельца на указанное отличие. Развёртывание само по себе НЕ включает уведомления и НЕ меняет Telegram webhook.

### Бесплатность не безлимитная

Нужны Workers Free, SQLite Durable Objects и **существующий** Redis/Upstash. Платные Containers, R2, VPS и платный план Workers не нужны. Но гарантировать бесконечную бесплатную работу нельзя: лимиты Cloudflare и Upstash действуют отдельно и совместно с другими приложениями аккаунта. Упор может быть не только в количество запросов, но и в длительность работы Durable Object во время ожидания внешних API. Если лимит Free исчерпан, приложение может перестать обслуживать запросы до обновления квоты; автоматически включать платный тариф не следует.

При интервале 10 секунд — до 8 640 циклов планировщика в сутки без учёта длительности работы. Активная вкладка делает два API-запроса каждые 5 секунд; несколько пользователей увеличивают расход. До постоянного использования проверить Usage и лимиты после тестового запуска. Бесплатную версию нельзя обещать как замену полноценному круглосуточному tick-stream серверу при любой нагрузке.

Официальные ограничения: https://developers.cloudflare.com/durable-objects/platform/pricing/ и https://developers.cloudflare.com/durable-objects/api/alarms/ . Alarms могут задерживаться и вызываться повторно. Планирование следующего запуска происходит после завершения текущего, поэтому фактический интервал больше 10 секунд.

## Сохранение существующих данных

Основные данные остаются в той же Redis-базе:

- `tg-alerts-db` — алерты, настройки новостей, покупки, заявки, события и счётчик;
- `tg-alerts:{h4}:settings:v1` и маркеры `tg-alerts:{h4}:sent:*` — H4;
- `tg-alerts:{live}:reminders:v1` — личные напоминания;
- `tg-alerts-news` — кэш календаря.

При недоступном Redis приложение не подменяет данные пустой базой. Одноразовый старый `resetV3` при миграции не запускается. SQLite Durable Object хранит только включение планировщика, историю Telegram update_id и служебные отметки. Один объект `production` последовательно обрабатывает изменения и проверки.

**До переключения:** сделать резервную копию существующей базы. Если старый Render хранил данные только в локальных файлах, эта версия НЕ переносит их автоматически. Не включать `ALLOW_EMPTY_STATE=true`, чтобы просто обойти ошибку: сначала нужен экспорт старых данных и импорт в Redis. Если данных больше не осталось, создание чистой базы допустимо только как отдельное решение владельца.

Старый Render TG Alerts необходимо оставить остановленным/удалить после резервного копирования: при его автоматическом пробуждении старый `getUpdates` может удалить новый webhook, а параллельные записи могут перетереть данные. Не останавливать исправный Access на Cloudflare.

## Настройки и секреты (значения не публиковать)

Runtime Secrets, Production, добавить **одной группой**, отметив Secret для каждого:

| Имя | Источник |
| --- | --- |
| `BOT_TOKEN` | Токен именно TG Alerts, НЕ `@verifycapp` |
| `ACCESS_SIGNING_SECRET` | Точно то же значение, что в работающем Access; НЕ генерировать заново |
| `TELEGRAM_WEBHOOK_SECRET` | Новый независимый секрет Alerts: 32–256 символов из `A–Z a–z 0–9 _ -`; длина 40 подходит, ровно 64 не требуется |
| `OANDA_TOKEN` | Действующий токен OANDA из старого окружения |
| `UPSTASH_REDIS_REST_URL` | Адрес той же базы Redis, что использовал Alerts |
| `UPSTASH_REDIS_REST_TOKEN` | Токен той же базы Redis |

Если раньше использовался Capital.com, также перенести `CAPITAL_API_KEY`, `CAPITAL_IDENTIFIER`, `CAPITAL_PASSWORD` как Secrets. Если указана только часть этих трёх значений, Capital не включается. Без Capital серебро в текущей конфигурации недоступно; Gold/GER40 доступны, только если они есть у OANDA. Поток Dukascopy эта версия не поддерживает — не переключает источник незаметно.

Проверить и перенести обычные переменные: `OANDA_ENV` (practice/live), `OANDA_ACCOUNT`, `OANDA_SIDE`, `OANDA_XAUUSD`, `OANDA_GER40`, `CAPITAL_ENV`, `CAPITAL_SIDE`, `CAPITAL_EPIC_*`, `OFFSET_*`, `ADMIN_CHAT_ID`, реквизиты `PAY_DETAILS`, цены/лимиты `PREMIUM_*`, `BASE_ALERTS`, `PRO_ALERTS`, `NEWS_MIRROR_URL`/`NEWS_URL`, если они реально использовались. Текущие значения в git: OANDA practice/mid; их нужно сверить со старым окружением, это не доказательство правильного режима счёта.

`PRICE_SOURCE=oanda`, `REQUIRE_ACCESS=true`. `AUTH_API_URL` указывает на уже работающий Access. `WEBAPP_URL` должен совпадать с фактическим production HTTPS-адресом Alerts; `https://tg-alerts.retocker.workers.dev` — ожидаемый, но после создания необходимо проверить.

Переменные, заданные в `wrangler.jsonc`, при следующих сборках берутся из git. Не рассчитывать, что ручная правка такой переменной в панели переживёт очередной deploy: согласованные изменения закрепить в миграционной ветке. Secrets в git не добавлять.

## Порядок развёртывания после согласия владельца

1. Сверить настройки/резервную копию Redis и оставить Render Alerts остановленным.
2. Подтвердить согласие на snapshot-режим; установить `SNAPSHOT_QUOTES_APPROVED=true` в миграционной конфигурации. До этого не активировать.
3. Создать **отдельный Worker `tg-alerts`**, подключив этот GitHub-репозиторий. Build command пустая; Deploy command `npx wrangler deploy`; Root `/`. После создания выбрать Production branch `cloudflare-migration`, не `main`. Если первоначально развернулась `main`, зелёный static build не означает работающего бота.
4. Workers Builds создаёт build API token автоматически. Никакую строку этого токена не нужно искать или вводить в приложение.
5. Миграция Wrangler создаёт SQLite Durable Object `AlertsEngine` и binding `ALERTS` автоматически, вручную D1 создавать не нужно. Добавить Production Runtime Secrets группой и выполнить один deploy.
6. Проверить `/health`: нужны `ok:true`, `runtime:cloudflare`, `quoteMode:snapshot`, `enabled:false`. Успешная сборка не проверяет наличие секретов или доступность брокера. `/health` проверяет хранилище, но не подтверждает получение котировок: после запуска проверить `/api/feed-status` и фактические цены.
7. Открыть `/setup.html`. Ввести **тот же `TELEGRAM_WEBHOOK_SECRET` Alerts**, который добавлен в Cloudflare. Не пароль от Access и не BOT_TOKEN. Нажать проверку; сверить username бота и количество сохранённых данных. Если числа неожиданные — остановиться, не подключать.
8. Отметить согласие на снимки и подтвердить подключение именно указанного бота. Только это регистрирует webhook и запускает scheduler.
9. Отправить `/start` в Alerts, открыть **новую** кнопку. Для входа использовать шестизначный код проекта Alerts из работающего Access. Проверить безопасный тестовый уровень, H4, Live и новости, статус брокера и Usage.

## Вход через работающий Access

Интерфейс отправляет код на `/api/access/redeem` того же Worker. Сервер обращается к существующему `/api/verify-code` Access и проверяет подпись результата для проекта `alerts`. Это избегает необходимости менять CORS работающего Access. Код, пароль и токены не записываются в логи.

Ограничение: Access может видеть общий IP Worker, поэтому его действующее ограничение попыток входа может делиться между пользователями Alerts. При `429` нужно дождаться указанного интервала, не повторять попытки бесконечно. При многопользовательском использовании отдельно согласовать прямой CORS-вход или доверенный механизм ограничения по клиентам; текущая версия не отключает защиту Access.

## Доставка и остановка

Это не exactly-once Telegram: API sendMessage не имеет ключа идемпотентности. Ценовой/новостной алерт помечается до отправки; таймаут может означать неопределённый результат, без слепого повтора. H4 сохраняет прежние Redis-маркеры; Live — прежние CAS-статусы pending/attempting/sent/unknown. Повторный успешный Telegram update_id игнорируется даже после перезапуска. При ошибке частично выполненной команды повтор может повторить часть ответа; не обещать отсутствие любых дублей.

Для остановки — POST `/admin/stop` с заголовком `x-setup-secret`, содержащим текущий секрет webhook Alerts, через доверенный локальный инструмент/консоль. Не вставлять URL с токенами в чат. Stop выключает scheduler, но не возвращает старый webhook автоматически. Удаление Worker тоже требует отдельного плана отката. Возврат на Render — только после остановки Cloudflare и восстановления старых настроек; одновременно два обработчика не запускать.

## Проверки без настоящего бота

Node 24: `npm ci`, `npm test`, `npm run test:cloudflare`.

Тесты Cloudflare используют настоящий локальный runtime workerd/SQLite Durable Objects с искусственными Redis/OANDA/Telegram/Access. Внешняя сеть закрыта mock-handler, настоящие секреты не нужны. Проверяются защита активации, покупки/данные, сериализация CRUD, подписи Access, ошибки Redis, свежесть котировок, webhook-дедупликация, запуск alarm и напоминания. Для реального E2E нужны доступные runtime-секреты и подтверждение пользователя в Telegram; локальные тесты этого не заменяют.
