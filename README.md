## Retocker Access
Set `AUTH_API_URL`, `ACCESS_SIGNING_SECRET` (the same value as the central access bot) and `REQUIRE_ACCESS=true`. Open TG Alerts, enter a code generated by the Retocker Access Mini App, and the session is stored in the browser for 96 hours.

## H4 candle reminders
Open **Settings → H4 candle reminders** in the Mini App. The feature is off by default
and never enables itself for existing users. Select assets, one or more lead times
(30/15/10/5/1 minutes), and optionally **At candle close**, then enable the master switch.
EUR/USD and GBP/USD are free; the existing ownership rules apply to the paid assets.
News preferences, price alerts and quote sources are unchanged.

### Timing and sources
- Uses the existing `OANDA_TOKEN` and `OANDA_ENV` (`practice`/`live`), and optionally
  `OANDA_ACCOUNT`. No new secret is required. Mock price mode disables H4 delivery.
- Fetches actual OANDA **H4** candles with explicit `dailyAlignment=17` and
  `alignmentTimezone=America/New_York`, not a hard-coded UTC or device-time schedule.
  Node's IANA timezone rules handle US DST; European DST does not shift this schedule.
- Pre-close reminders need a current nonempty incomplete candle **and** OANDA's
  `tradeable=true`. Broker-reported session breaks/holidays suppress pre-close reminders.
  This is not a predictive holiday calendar: exceptional early closes cannot be
  announced in advance solely from these API fields.
- The close message requires OANDA's `complete=true`; the countdown reaching zero
  does not confirm completion. Polling normally adds up to roughly 10–30 seconds,
  plus OANDA/Telegram/network delay. A later outage does not produce stale catch-up spam.
- Gold/GER40 reminder candles are **always OANDA**, even when the app's prices come
  from Capital.com. Existing `OANDA_XAUUSD`/`OANDA_GER40` overrides apply. If those
  instruments are unavailable on the OANDA account, their timers report unavailable;
  no other broker is silently substituted.
- DXY is not offered for H4 reminders. Old DXY selections are ignored; its prices
  and price-level alerts remain unchanged.
- This explicitly implements OANDA v20's 17:00 New York alignment. A chart using
  different candle/session settings must be compared before assuming a visual match.

### Persistence and operational requirements
> Redis/Upstash and `DB_FILE` notes in this and the Live section describe the store modules' standalone mode used by tests. Production runs on Cloudflare: data lives in the Durable Object's SQLite, see [CLOUDFLARE.md](CLOUDFLARE.md).

- Telegram `/start` is still required before the bot can message a user.
- H4 preferences use a separate Redis hash `tg-alerts:{h4}:settings:v1`, so a
  news-settings save cannot overwrite them. Delivery claims use per-event `SET NX`
  with a two-day expiry to suppress repeats across restarts and overlapping deployments.
- Without Upstash, preferences and claims are atomically saved in `DB_FILE + '.h4.json'`.
  This is only restart-safe on a **persistent disk and a single server process**.
- Redis failure blocks H4 sends instead of falling back to non-durable state. A failed
  settings save is visibly reported. A delivery is claimed before sending; ambiguous
  Telegram failures are reported to the admin and not blindly retried (Telegram does
  not provide an idempotency key for sendMessage). Thus no exactly-once guarantee is made.
- Missed pre-close reminders older than one minute and closes older than two minutes
  are not replayed. Settings changes take effect locally immediately; overlapping
  instances reload preferences at most 30 seconds later; an atomic Redis preference
  check at delivery time rejects stale instances immediately.
- **Cloudflare production:** reminders run through Durable Object alarms and persist
  in SQLite.

### Tests
`npm test` runs without OANDA/Telegram credentials, npm dependencies, or external API
calls: timezone/DST boundary cases, both US/Europe transition gaps, weekend/holiday
suppression, completion checks, delivery windows, preferences, durable deduplication,
and quote authorization.

## Live personal reminders
The **Live** tab adds personal Telegram reminders. Tap **+**, enter text, a start
date, timezone and up to six times. Repeat once, daily, on weekdays or weekly;
choose 1–90 notification days/weeks. Two times × three days = six notifications.
Pause/resume, edit and delete are available. No premium quote purchase is needed.

- The timezone defaults to the device IANA timezone and is saved per reminder.
  Recurrences keep local wall time across DST, not a fixed +24-hour offset.
  Ambiguous fall times occur once (earlier occurrence). Nonexistent spring times
  are rejected with the exact date/time so a different time can be selected.
- API routes `/api/live` (GET/POST) and `/api/live/:id` (PUT/PATCH/DELETE) use the
  existing authenticated user. Server validates all dates, times, lengths and limits.
  Times that already passed (e.g. earlier today) are skipped; the rest are scheduled. Editing replaces the schedule;
  past deliveries are not replayed. Count means days/weeks, not total messages.
- Separate Redis hash `tg-alerts:{live}:reminders:v1` stores each reminder including
  its finite schedule and delivery outcomes. Lua compare-and-swap prevents stale
  edits and duplicate claims across overlapping deployments. Max 100 saved reminders
  per user, including finished ones. Delete old reminders to free space.
- Without Redis, atomic writes use `DB_FILE + '.live.json'`: persistent disk and a
  single process are required. Redis failures fail closed, never fall back to empty
  state.
- A client-generated UUID makes create retries idempotent. Edits/deletes require
  the latest revision. Ambiguous saves show Reload; the UI never auto-repeats a write.
- Scheduler checks every 10 seconds while the process is running, independently
  of market hours/OANDA. Sends delayed reminders up to 15 minutes late; older ones
  become **Missed**. Paused occurrences are not replayed on resume.
- Claim is durable before Telegram send. Confirmed response -> Sent; rejection ->
  Failed; timeout/crash -> Delivery not confirmed. Unknown sends are not blindly
  retried: Telegram cannot guarantee exactly-once sendMessage. Errors do not expose
  private reminder text in admin logs. Messages are plain text, not HTML.
- Tests include real Redis Lua (when redis-server is installed), competing runners,
  durable restart, paused/deleted reminders, storage/network failures and DST. CI installs
  Redis and runs on Node 20/24; no real accounts or user notifications are touched.
